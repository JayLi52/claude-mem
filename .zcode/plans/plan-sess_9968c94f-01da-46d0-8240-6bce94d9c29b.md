# 记忆召回计数（Recall Tracking）实现方案

## 背景
claude-mem 目前没有任何召回统计。`observations` 表有一个 v26 加的 `relevance_count` 列，但**从未被任何代码写入**——本方案就是补上这个缺口，为将来"按召回率清退"提供数据基础。

## 设计决策（已定）
- **口径**：全口径记录，所有召回出口都计数，用来源标记区分信号强度
- **存储**：专用计数器列（纯本地，仿 `relevance_count` 先例，不参与同步）
- **范围**：本轮只做计数，清退命令后续再做

## 实现步骤

### 1. Schema 迁移 — `src/services/sqlite/SessionStore.ts`
- 新增私有方法 `addObservationRecallStatsColumns()`，照抄 `addObservationModelColumns()`（L1687-1702）的模式：PRAGMA table_info 检查 → `ALTER TABLE observations ADD COLUMN recall_count INTEGER DEFAULT 0` + `ADD COLUMN last_recalled_at_epoch INTEGER` + `ADD COLUMN last_recall_source TEXT` → 记 schema_versions 新版本号
- 在构造函数迁移链（L91-122）末尾、`normalizeConceptTags()` 之前调用
- 不改 `relevance_count`（保留历史列）

### 2. 新增 RecallTracker 服务 — 新文件 `src/services/worker/RecallTracker.ts`
- 接收 `(ids: number[], source: RecallSource)`，进程内 Map 累加（burst 合并），CloudSync 式 debounce（~1.5s，timer unref）后单条批量 SQL 落库：
  `UPDATE observations SET recall_count = recall_count + ?, last_recalled_at_epoch = ?, last_recall_source = ? WHERE id = ?`
- **绝不触碰 `synced_at` / `sync_rev`**（否则会触发 CloudSync 重推）；CloudSync drain 用显式列清单（CloudSync.ts:179-218），新列自动不会被同步，与 `relevance_count` 同理（SyncApply.ts:49-51 注释先例）
- fire-and-forget，失败只打 log 不抛错（仿 MemoryRoutes.ts:85-94 惯例）
- RecallSource 枚举：`search` | `semantic_inject` | `context_inject` | `detail` | `timeline`

### 3. 埋点（6 个点位，worker 侧）
| 点位 | source | 取 id 方式 |
|---|---|---|
| `SearchManager.search()` 结果定型处（json/text 两分支前） | `search` | `observations[].id` |
| `SearchManager.searchObservations()`（/api/search/observations） | `search` | `results[].id` |
| `SearchRoutes.handleSearchByFile` L190 后 | `search` | `observations[].id` |
| `SearchRoutes.handleSemanticContext` L404 后（只计 `slice(0, limit)` 实际注入的） | `semantic_inject` | top-N ids |
| `DataRoutes.handleGetObservationsByIds` L175 后（只计实际返回的） | `detail` | `observations[].id` |
| `ContextBuilder.generateContextWithStats` L198 后 | `context_inject` | `observations[].id` |

注：timeline 端点本轮先不埋（信号弱、组装复杂），source 枚举预留。

### 4. 暴露计数
- `SessionSearch.searchObservations` 和 `getObservationsByIds` 都是 `SELECT o.*`，新列自动带出 → 在 `src/services/sqlite/types.ts` 的 `ObservationRow` 上补可选字段声明（`recall_count?`、`last_recalled_at_epoch?`、`last_recall_source?`），JSON 响应自然可见
- ContextBuilder 直连 SQL 是显式列清单（ObservationCompiler.ts），不额外 SELECT 新列（注入文本不需要计数）

### 5. 测试
- 迁移幂等性（重复开库不报错）
- RecallTracker debounce 合并 + 落库正确性
- 同步隔离回归：确认计数 UPDATE 后 `synced_at`/`sync_rev` 不变、CloudSync drain 不拾取

## 不做的事
- 不加 recall_events 日志表（后续有需要再加）
- 不做清退/删除命令（等数据积累）
- 不动 server runtime（`CLAUDE_MEM_RUNTIME=server`）的 /v1 路径——你本地跑的是 worker 模式

## 验证
`npm run build-and-sync` 后，触发几次 MCP search 和语义注入，查 `sqlite3 ~/.claude-mem/claude-mem.db "SELECT id, title, recall_count, last_recall_source, datetime(last_recalled_at_epoch/1000,'unixepoch') FROM observations WHERE recall_count > 0"` 确认计数生效。
